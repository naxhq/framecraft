# v3-04 - Phase 4 UI: PRINTER group, Issues drawer, estimates, tiling

Scope: `apps/web/**`, coordinating with the parallel `p4-engine` builder who
owns `lib/engine/**` and `scripts/bake-cli.ts`. Everything below is UI/store
work built against `lib/engine/types.ts`'s `AuditFinding`/`TileResult`/
`EstimateResult` and `lib/engine/audit/fixes.ts`'s `applyFix`/`applySafeFixes`
(both landed by p4-engine mid-task; nothing under `lib/engine/**` was
hand-edited).

## 1. PRINTER group and profile-apply

New `apps/web/components/editor/groups/PrinterGroup.tsx` (`lib/groups.ts`, id
`"printer"`, collapsed by default, positioned between Colour and Output). The
printer-profile select and the custom-profile sliders were MOVED here out of
`ColourGroup.tsx` (they lived there only because filament slot count feeds the
Colour group's own "exceeds this profile's slots" warning, which still reads
`resolveProfile(params).slots` from `ColourGroup.tsx`, unchanged).

Profile-apply: `store.setPrinterProfile(id)` (new action) writes
`printer_profile` and, for every NAMED printer (never `custom`), also
`plate_mm`/`nozzle_mm` from the profile -- once, on the selection change
itself, via `lib/printers.ts:profileApplyPatch(id, ranges)` (new, tested in
`lib/printers.test.ts`). `plate_mm` takes the SMALLER of the profile's two bed
dimensions (a square print cannot exceed a non-square bed's short side),
clamped into `plate_mm`'s own `PARAM_RANGES` (not the profile's raw numbers,
which exceed it for the H2S: 340 x 320 mm bed against a 256 mm contract
ceiling). The user can move `plate_mm`/`nozzle_mm` freely afterwards; nothing
fights them back. Selecting `custom` writes only the id.

TILING lives in the same group (own subsection, not a separate top-level
group): `tiling.enabled/cols/rows/joint/tolerance_mm/index_mark`, all through
`setNested("tiling", ...)`, ranges from `PARAM_RANGES.tiling`.

## 2. The height ceiling: `heightCeilingMm` ([V3-P4-U], provisional)

`lib/warnings.ts:heightCeilingMm(params) = resolveProfile(params).maxHeightMm`
(straight, no `Math.min`), read by `OutputPanel.tsx`'s "Predicted height X mm
of Y mm" line, `lib/hud.ts`'s HUD tone and `CityPreview.tsx`'s too-tall pill
(all three previously hardcoded to the flat `T.MAX_HEIGHT_MM`, 60 mm). This
matches the phase 4 brief's own worked example exactly: selecting a P1S makes
the line read "of 250 mm".

This went through an interim state worth recording, because it is exactly the
kind of cross-agent race this run's `DECISIONS.md` exists to catch. A straight
replacement is only safe once `custom_profile.max_height_mm`'s CONTRACT
default is 60 (not its original 250): every `PrintParams` starts on
`printer_profile: "custom"`, so with the old 250 default a straight
replacement would have silently raised the ceiling for every session that
never opens the Printer group at all -- a real regression against 04's frozen
60 mm invariant. This agent shipped `Math.min(T.MAX_HEIGHT_MM,
resolveProfile(...).maxHeightMm)` first (safe under either contract default),
flagged the conflict to the orchestrator and to p4-engine (whose
`validate.ts:maxHeightMm(ctx)` had the identical pattern), and flipped to the
straight replacement the moment the regenerated contract
(`custom_profile.max_height_mm` 250 -> 60, `[V3-P4]`/`[V3-P4-E9]` in
`DECISIONS.md`) was observed on disk -- one line in `heightCeilingMm`, two
test expectations in `warnings.test.ts` and one in `printers.test.ts`,
`e2e/print.spec.ts`'s P1S test rewritten to assert "of 250 mm" (verified
against a real browser afterward, not assumed).

`predictedTopDeps` (== `previewDeps.height`) now also lists
`params.printer_profile` and `params.custom_profile?.max_height_mm`: neither
moves the predicted top itself, only the ceiling it is compared against for
the HUD tone / too-tall pill, so this is the one honest over-inclusion in that
list (`warnings.test.ts`'s closed-set check tolerates it; it only fails if a
REAL dependency of the prediction is missing). `CityPreview.test.ts`'s
`V3_ENGINE_MOVES` "rebuilds nothing" bucket had these two keys moved out into
their own asserted-real test, mirroring the existing `hero_auto` carve-out in
the same file.

## 3. Issues drawer

New `lib/issues.ts`: `Issue{id, severity, title, detail, region?, fix?,
source}`, `mergeIssues(warnings, findings)` (client `SceneWarning`s from
`lib/warnings.ts` folded in first, then engine `AuditFinding`s -- a shared id
lets the engine's row win outright), `groupIssuesBySeverity`, `issueCounts`,
`issuesLabel`, `safeFixesSummary`. Re-exports p4-engine's `applyFix`/
`applySafeFixes`/`hasSafeFixes` from `lib/engine/audit/fixes.ts` rather than
wrapping them (this agent had written a local reimplementation before finding
that module; dropped in favour of the real one, which deep-merges nested
patches and reports `FixChange[]`).

New `components/editor/IssuesBadge.tsx`, mounted in `CityPreview.tsx` next to
(not replacing) the existing `AdjustmentsChip` -- see `[V3-P4-U]` in
`DECISIONS.md` for why this is additive rather than the brief's literal
"single widget": `AdjustmentsChip`'s category grouping is named directly by
three existing e2e specs and its own vitest suite, and rewriting it into
severity groups was judged out of this task's remaining budget against the
risk of weakening those. `IssuesBadge` groups by severity (error/warning/
info), each row a title + plain-language detail, a real fix button wherever
`issue.fix` exists (`store.applyFinding`), and an "Auto-fix all safe issues"
button (`store.applySafeFindingFixes`) reporting what changed. Both store
actions are one `set()` call each -- stale-marks the engine/bake and
reschedules a bake exactly like `setParam`.

## 4. OUTPUT estimate block

New `components/editor/EstimateCard.tsx`: per-slot rows (colour dot, grams,
metres), a total, and a print time RANGE (`seconds * 0.75` to `seconds *
1.5`, a UI-only spread around `lib/engine/estimate.ts:estimate()`'s single
point value -- documented in the component as not derived from anything, just
a way to say "rough" that a lone number cannot), all under an "estimate"
label, from `estimate(result, result.params)` run on the live
`state.engine.result`. Skeleton while `engine.status === "computing"`; nothing
when there is no result yet.

Real bug found by actually running `e2e/print.spec.ts` rather than trusting
the design: `EstimateCard` was first placed OUTSIDE the OUTPUT group's
existing `showResults` collapse (reasoning: "before baking" should mean
always visible). A real screenshot from a failing test showed why that was
wrong -- with a real bake's slot rows, total and caveat paragraph, the OUTPUT
section (a `shrink-0` sibling of the scrollable group list in
`ParamPanel.tsx`'s flex column) grew tall enough to squeeze that scrollable
area to zero visible height, making every group below it (and the Printer
group specifically, which is what the failing test was trying to open)
unreachable.

Two fixes, in order, because the first was necessary but not sufficient.
First: moved `EstimateCard` inside the `showResults`-gated results block,
alongside `StatsCard`/the resolved-output panel/bake status. Re-running
`e2e/print.spec.ts` still failed the same way (`group-output intercepts
pointer events` on the Printer group's toggle, and on Colour's, two groups
further up) -- `showResults` defaults to TRUE, so the product's own default
state already carries this content, and the first fix only helps once a user
manually collapses it. Confirmed this is pre-existing (`StatsCard` and the
resolved-output panel alone, with no `EstimateCard` at all, already reach the
same overflow on the default 1280x720 viewport once a real bake has produced
content) and made measurably worse by this phase's own additions. Second, the
real fix: the results `<div id={resultsId}>` is now `max-h-[45vh]
overflow-y-auto`, scrolling internally rather than pushing the sidebar's
bottom edge past its own bounds; the action row, the predicted-height line
and the block-reason note stay outside the cap, so Bake itself can never be
scrolled out of reach. This introduced its own, caught-immediately regression
(section 6) -- axe's `scrollable-region-focusable`, since a fresh scroll
region needs a focusable node of its own -- fixed with `tabIndex={0}`, the
same discipline `AdjustmentsChip`'s drawer already uses. Verified end to end:
`e2e/print.spec.ts`'s four tests, previously timing out at 300 s each with
this symptom, pass in 24.7 s total against a real (production-mode) browser.

## 5. TileGrid and the tiled-export note

New `components/scene/TileGrid.tsx`: one rectangle outline
(`@react-three/drei`'s `Line`, a real `THREE.Object3D`, not a DOM node) per
`EngineResult.tiles[]`, a hair above that tile's own tallest point, plus a
grid-reference label (`TileResult.label`, e.g. "A1") anchored with drei's
`Html` (real DOM, unlike `Line`) at the tile's centre. Colour comes from a new
design token, `--fc-preview-tile-line` (`app/globals.css`, both themes;
`components/scene/palette.ts`'s `PreviewPalette.tileLine`), never a raw hex or
a `var()` string passed to a `THREE.Color`. Mounted in `CityPreview.tsx` next
to `RegionMeshes`, only while a fresh engine result exists.

`ExportMenu.tsx` gained a note, shown only when `state.engine.result.tiles`
has more than one tile, naming the real count and labels. Checked against
every exporter file rather than asserted from the brief's own wording: only
`bambu-3mf`/`color-change-3mf` are tile-aware today
(`lib/engine/export/bambu3mf.ts`, one plate per tile, p4-engine's work);
`generic-3mf`/`stl`/`stl-parts-zip`/`obj`/`step` still export the whole
assembled model in one piece regardless of `params.tiling`. The note says
this plainly for the non-Bambu targets rather than promising a per-tile file
those exporters do not produce (`[V3-P4-U]`).

## 9. CI-runner budget fixes (team lead's Phase 3 CI report)

Two failures on the ubuntu CI runner (2-core software WebGL), both timing,
neither a real assertion failure, folded into this phase since it owns e2e
and pushes next:

- `e2e/a11y.spec.ts`: "every control is reachable by Tab, in order, with a
  visible focus ring" hit Playwright's own 300 s TEST timeout (separate from
  any one `expect(...).toBeVisible({timeout})`) 5.1 min into the 120-press
  walk. The file gained `BUDGET_FACTOR` (it had none before) and
  `WARMUP_BUDGET_MS` now scales with it; the tab-walk test and the axe test
  both call `test.setTimeout(300_000 * BUDGET_FACTOR)`. The tab walk also now
  waits for `engine-updating` to clear before it starts, so its 120 presses
  are not competing with the debounced WASM job's own store-wide re-render
  landing partway through.
- `e2e/smoke.spec.ts`: "the downloaded file passes the Python printability
  validator (full Chicago scene)" failed a bare `expect(bakeButton).
  toBeEnabled()` (the config default 15 s) at full Chicago complexity (992
  buildings). Given `{timeout: WARMUP_BUDGET_MS}` (already scaled in this
  file); the assertion itself -- enabled, not merely present -- is unchanged.

Both re-verified locally (`FRAMECRAFT_WEB_MODE=prod`, `E2E_BUDGET_FACTOR`
unset i.e. 1): identical pass, no behaviour change at the default factor.
