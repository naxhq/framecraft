runs, on the fast path or the nightly one, and both keep every zero-skip guard.

## 2. The new job graph

```
push / pull_request  ->  ci.yml          REQUIRED, five parallel jobs
                         ├─ lint-typecheck     no-skip guard, eslint, tsc
                         ├─ unit               vitest + zero-skip check
                         ├─ pytest             reference service + zero-skip check
                         ├─ build-and-validate next build, 2x export:cli, validator
                         └─ e2e-smoke          the @smoke subset + results.json guard

03:30 UTC daily      ->  nightly.yml     five jobs
workflow_dispatch        ├─ e2e-full           the whole Playwright suite
push tag v*              ├─ geometry-gates     make gate-v2
                         ├─ export-matrix      7 targets + 2x2 tiling
                         ├─ preset-matrix      6 presets offline
                         └─ desktop            3 installers (skipped on the tag trigger)

push tag v*          ->  release.yml     create-release, desktop, web-zip
                         └─ desktop calls desktop-build.yml with a tag to attach to

push to main         ->  pages.yml       unchanged
```

`desktop-build.yml` is new: the Tauri matrix as one reusable workflow with two
callers, so release.yml and nightly.yml cannot drift. `release.yml`'s `desktop`
job is now a five-line `uses:` block; its steps moved verbatim.

Concurrency: `ci.yml` keeps `ci-${{ github.workflow }}-${{ github.ref }}` with
`cancel-in-progress: true`. `nightly.yml` uses `nightly-${{ github.ref }}` with
`cancel-in-progress: false`, because cancelling a half-finished nightly proves
less than letting it finish.

The three tagged tests cover preview, two different export targets, a download,
a validator verdict on the downloaded bytes, and the empty-coverage refusal

**Measured end to end**, `npm run test:e2e:smoke` from a cold `.next` with
nothing else running, which includes starting uvicorn, starting `next dev`,
the first-page compile and all three tests:

| | Time |
|---|---:|
| Whole command, cold | **62s** |
| The three tests alone | 26.8s (4.7s, 17.1s, 5.0s) |
| Server boot plus first compile | about 33s |

Against `npm run test:e2e` on the same host at 8.6 minutes for the whole suite.

**The happy path is deliberately not tagged**, and that is the one judgement
call in this task worth arguing with. It is the most representative single
test in the repo. It is also 2m 12s here because it builds all 992 Chicago
buildings, measures a slider-driven frame rate and nudges the rotation twice.
GitHub's runners have no GPU and fall back to SwiftShader, where the suite runs
2.2x to 3.7x slower than this host (baseline: 19 to 32 minutes there against
8.6 minutes here). That projects the happy path alone at 5 to 8 minutes, which
spends the whole seven-minute budget on one test. Full-Chicago geometry is not
lost from the fast path: `build-and-validate` exports the same 992-building
fixture twice through `export:cli` and the validator judges both files. The
UI-side happy path runs nightly.

If the first measured `e2e-smoke` job lands comfortably under four minutes,
promoting the happy path back into `@smoke` is a one-line change and is the
first thing to reconsider.

Two projects now exist in `playwright.config.ts`: `chromium` (every test, what
`npm run test:e2e` and every full gate run) and `chromium-smoke` (the `@smoke`
grep, what `npm run test:e2e:smoke` runs). Verified with `--list`: 3 tests in 1
file for the smoke project, and the whole suite for `chromium`. A tag selects;
it never excludes.

Absolute suite sizes are deliberately not written into the workflows or the
config. The suite was 50 tests when this split was designed, 60 when it was
audited and 67 an hour after that. Only the tagged count is stable, and only it
is asserted (the smoke job fails if the grep selects fewer than three).

`--grep` filters at collection, so an unselected test is absent from
`results.json` rather than reported as skipped. That means a mistyped tag would
run zero tests and still print a green tick, so the smoke job and `make
gate-fast` both assert that the grep selected at least three tests, on top of
the zero-skip and zero-expected-failure walk they share with the full suite.

## 4. Projected per-job times, fast path

Projected from the baseline's per-step numbers for run 33611314264, warm
caches, plus ~10s per job of cache restore and reporting.

| Job | Projection | Dominated by | Timeout |
|---|---:|---|---:|
| `lint-typecheck` | 0m 50s | npm ci 12s, eslint 7s, tsc 9s | 10m |
| `unit` | 3m 05s | vitest 2m 31s | 10m |
| `pytest` | 3m 20s | pytest 2m 50s | 10m |
| `build-and-validate` | 2m 15s | next build 37s, two exports 21s, validate 11s | 10m |
| `e2e-smoke` | 3m 30s to 5m 40s | setup 2m, server boot 1m to 2m, tests 30s to 100s | 10m |

The `e2e-smoke` projection takes the measured 62s and inflates the parts that
are runner-sensitive: the three tests by the 2.2x to 3.7x SwiftShader factor
the baseline implies, and the dev-server boot by two to three times for a
two-core runner, then adds 2m of setup steps.

All five run in parallel, so the projected wall-clock is the slowest, between
**3m 30s and 5m 40s**, against a 25m 30s baseline. Even at the pessimistic end
plus a minute of queueing, the required path stays inside ten minutes.

Every timeout is **10 minutes**, which makes the budget an assertion rather than
a claim. They were originally 10 to 15, sized per job at three to four times the
projection, until the audit pointed out that a hung job could then hold the
required path for fifteen minutes and still be reported as "under budget". A
single number equal to the budget is the check: if any required job needs more
than ten minutes, the fast path has stopped being fast and should fail rather
than quietly stretch. The pessimistic `e2e-smoke` projection of 5m 40s leaves
roughly four minutes of headroom against it.

### The export matrix, honestly

`services/bake/app/cli.py` refuses anything but `.3mf` and `.stl`, which rules
the validator out for stl-parts-zip, obj and step. bambu-3mf and
color-change-3mf are `.3mf` and the validator accepts them, but a Bambu project
puts its mesh in `3D/Objects/object_1.model` rather than `3D/3dmodel.model` and
the structural checks do not resolve through that indirection. Run against the
full Chicago build it did not finish: **14 minutes of wall clock and 22
CPU-minutes before it was aborted**, against 11 seconds for the two generic-3mf
files the required path validates on every commit. A check that cannot finish
is not a check.

So `scripts/ci-export-matrix.sh` prints two kinds of row and says which each
target got:

| Target | Judgement |
|---|---|
| generic-3mf, stl | `make validate`, ALL CHECKS PASS asserted |
| the four 2x2 tiles | `make validate` each, ALL CHECKS PASS asserted |
| bambu-3mf, color-change-3mf | zip magic, `3D/3dmodel.model`, `3D/Objects/`, `Metadata/` present |
| stl-parts-zip | zip magic and at least one `.stl` member |
| obj | `mtllib` header and the companion `.mtl` actually written |
| step | `ISO-10303-21` and `FILE_SCHEMA` present |

A structure row is weaker than a validated one. It relaxes nothing, because
before this script no CI job built those five targets at all.

### The preset matrix, honestly

All six presets run through the reference pipeline
(`python -m app.cli bake --preset <id>`), which sets `allow_network=False` and
reads the committed `fixtures/<sha1>.json`, so it is fully offline. Each output
is validated as both `.3mf` and `.stl`.

The browser engine covers Chicago only. `export-cli.ts` hard-codes
`DEMO_CENTER` (the Chicago Loop) as the centre for `--overpass` and has no flag
to override it, because a raw Overpass response carries no centre of its own.
Feeding it the Paris fixture would crop Paris data around a point in Illinois
and build an empty plate. **Open gap:** a `--center lat,lon` flag on
`export-cli.ts` would let all six presets run through the browser engine too.
That is application source this task did not own.

## 7. Caching, and what is actually asserted

Every cache is keyed explicitly rather than by `setup-node`'s or `setup-uv`'s
internal key, so the key is a value the workflow can name, print and assert on.
`enable-cache: false` on `setup-uv` and no `cache: npm` on `setup-node`.

| Cache | Path | Key | Assertion |
|---|---|---|---|
| npm | `~/.npm` | `npm-<os>-<hash of apps/web/package-lock.json>` | fails on a warm miss |
| uv | `~/.cache/uv` | `uv-<os>-<hash of services/bake/uv.lock>` | fails on a warm miss |
| Playwright browsers | `~/.cache/ms-playwright` | `playwright-<os>-<@playwright/test version read out of the lock file>` | fails on a warm miss |
| next build | `apps/web/.next/cache` | lock hash + hash of `app/`, `components/`, `lib/`, `store/`, `public/` and the configs | reports only |

**What is asserted.** `.github/actions/cache-report` writes one row per cache
into `$GITHUB_STEP_SUMMARY` and fails the job on a WARM MISS, defined as: the
restore reported a miss, while the repository cache API lists an entry with
that exact key, on a ref this run was allowed to read (its own ref, or the
default branch, which a pull request may read from), created before
`github.run_started_at`. That last clause is what stops a sibling job in the
same run from causing a false failure when both jobs miss and the first one
saves the key.

**What is not asserted, and why.** The brief's literal form was "on a
`pull_request` or push when `cache-hit != 'true'` AND the lock file is
unchanged from the base". That is not directly expressible, and it is also
weaker than it sounds: a lock file can be unchanged from the base and still
have no cache, on the first run after this workflow lands or after a cache
eviction, and a hard failure there would be red for no defect. Querying the
cache API is strictly stronger, because it distinguishes "the key exists and we
missed it" from "the key has never existed". Because the API answer is
available, the fallback the brief allowed (report the hit rate, add a weekly
job that fails on two consecutive npm misses) was not needed and is not
implemented.

**Where it has teeth, and why not everywhere.** `cache-hit != 'true'` is not
produced only by "the entry was absent". `actions/cache` swallows restore
errors and reports a miss on a cache-service outage; it also matches on an
internal version derived from the path list, so a path changed in one workflow
and not another misses forever while the API keeps listing the other's entry;
and an eviction between the restore step and the report step looks the same.
Any of those would have turned an unrelated pull request red on somebody else's
incident (audit M2). So the failure now fires only on a push to the default
branch, where a red run reaches a maintainer instead of blocking a contributor.
Everywhere else the same row is printed and raised as a `::warning::`. The check
still fails, on the branch that matters, for the condition it was written to
catch; nothing is hidden anywhere.

Four remaining limits:

1. It needs `actions: read`, which both workflows grant. If the API is
   unreachable (an outage, a fork PR token) the row reads "warmth NOT asserted"
   and the job does not fail. It never passes silently.
2. It cannot see caches scoped to a ref this run may not read, so a genuine
   cross-branch cache miss reads as cold.
3. The `next build` cache reports but never fails: a first build on a new
   branch is a legitimate miss. `restore-keys` gives it a warm start from the
   previous build on the same lock file.
4. `created_at` is compared to `github.run_started_at` as strings. The API
   returns fractional seconds and `run_started_at` does not, so an entry created
   in the same second as the run start sorts as "before". A one-second window,
   harmless in practice.

**Cache budget.** The `next build` key was originally lock hash plus a hash of
the source, which minted a new multi-hundred-megabyte entry on every single
commit and pushed the repository toward the 10 GB cache ceiling, where GitHub
evicts least-recently-used entries first. The entries first in line were exactly
the ones not rewritten per commit: npm, uv, and the Playwright bundle that costs
3m 46s to re-download. A caching scheme that evicts the caches the budget
depends on is worse than none, so the key is now lock hash plus branch name and
`restore-keys` supplies the warmth (audit M3).

One duplicate remains and is accepted: `release.yml`'s `web-zip` and
`desktop-build.yml` still use `setup-node`'s built-in `cache: npm`, which
caches the same directory under a different key (audit minor 8). Hand-rolling
the key there would be wrong rather than merely more work, because `~/.npm` is
not the npm cache path on Windows or macOS and `desktop-build.yml` runs on all
three. The cost is one extra entry per lock file, which the M3 fix more than
pays for.

The Playwright browser cache is keyed by the `@playwright/test` version alone,
not by the whole lock file, so an unrelated dependency bump does not throw away
a download the baseline measured at 3m 46s. On a hit the job runs
`npx playwright install-deps chromium` for the apt libraries, which are outside
`~/.cache`; on a miss it runs `install --with-deps`.

## 8. Make targets

| Target | What it is |
|---|---|
| `make gate` | unchanged. The full local gate, every e2e test, the whole lifecycle. |
| `make gate-fast` | the required CI path locally: the same guards, pytest, lint, tsc, vitest, `next build`, the browser-engine export and validate, then the `@smoke` subset. |
| `make gate-nightly` | `make gate` + `make gate-v2` + the export matrix + the preset matrix. Every step is attempted even after an earlier failure, so one command reports everything that is red. |

`make gate-fast` uses `playwright.config.ts`'s Safe Order 3 (build, then
`rm -rf .next`, then run), so Playwright's own `webServer` owns the stack and
there is no `make up`/`make down` pair. `make gate-nightly` cannot build the
macOS and Linux installers; the nightly `desktop` job is the only place all
three run.

Both new recipes were syntax-checked with `sh -n` after `$(MAKE)` and `$$`
substitution: 4,323 bytes and 976 bytes, well inside the 8 KiB argument limit
the ezwinports make on this host imposes (the limit that put
`gate-web-engine.sh` in a file in the first place, and the reason
`ci-export-matrix.sh` and `ci-preset-matrix.sh` are files too).

## 9. Validation performed

- Every workflow and action file parses: `ci.yml`, `nightly.yml`,
  `desktop-build.yml`, `release.yml`, `pages.yml`,
  `.github/actions/cache-report/action.yml`, checked with PyYAML through
  `uv run --with pyyaml` in `services/bake`.
- `scripts/ci-export-matrix.sh` and `scripts/ci-preset-matrix.sh` pass `sh -n`.
- `make help` runs, so the Makefile parses; both new recipes pass `sh -n` after
  `$(MAKE)` and `$$` substitution.
- `npx playwright test --project=chromium-smoke --list` reports exactly the 3
  intended tests, and `--project=chromium` still reports the whole suite.
- The full Playwright suite was run locally for the per-test timings.
- `npm run test:e2e:smoke` was run locally from a cold `.next`: 3 passed, 62s.
- The export matrix and the preset matrix were both run locally end to end.

Do not use `make -n` on `gate`, `gate-fast` or `gate-nightly`. GNU make
executes a recipe line containing `$(MAKE)` even under `-n`, and all three are
one backslash-continued line that contains it, so a dry run is a real run. That
is how the recipes were checked here instead: extract the body, substitute, and
run `sh -n` on it.

`act` is not installed on this host and nothing was installed globally, so the
workflows have not been executed. `gh workflow view` needs them pushed first.
