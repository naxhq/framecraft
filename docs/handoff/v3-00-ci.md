# v3-00: CI workflow

`.github/workflows/ci.yml` for `naxhq/framecraft` (public repo, default branch
`main`). Runs on push to `main` and on every pull request, `ubuntu-latest`,
`permissions: contents: read`, `concurrency` cancels a superseded run on the
same ref.

## Jobs (parallel)

- **bake-service** (timeout 15 min): `astral-sh/setup-uv@v5` pinned to
  `0.12.1` (the version verified on the dev host), cache on
  `services/bake/uv.lock`, `uv sync`, `uv run pytest -q -rs`, then a grep on
  the captured log for `skipped|xfailed|xpassed` (pytest exits 0 on a skip;
  this is the same idea as `make gate`'s step 2). No ruff step: ruff is a dev
  dependency but is not run by `make gate` or `make test` on this host (it is
  blocked by a Windows Application Control policy, DECISIONS `[P1]`), so a
  ruff step here would be a new, unreviewed gate, not a reproduction of one.
- **web** (timeout 15 min): the static no-skip guard (mirrors `make gate`
  step 1, apps/web spec files only) runs first since it needs no
  dependencies, then `actions/setup-node@v4` (Node 22, npm cache keyed on
  `apps/web/package-lock.json`), `npm ci`, `npm run lint`, `npm run
  typecheck`, `npm test` with the same `skipped|todo` grep `make gate` step 3
  uses, `npm run build`. Uploads nothing.
- **e2e** (timeout 30 min): `setup-uv` + `uv sync` (services/bake) and
  `setup-node` + `npm ci` (apps/web), `npx playwright install --with-deps
  chromium`, then `npm run test:e2e` directly. `playwright.config.ts`'s own
  `webServer` array starts `uv run uvicorn` on :8000 and `next dev` on :3000
  and health-waits both, so this job does not `make up`/curl-poll by hand;
  it is exactly the config's documented "Safe Order 1" (`npm run test:e2e`
  alone on a tree no build has touched since this checkout), which sidesteps
  the `next build`-vs-`next dev` `.next` race the config warns about at
  length. `FRAMECRAFT_OFFLINE` is left empty (not set to a truthy value),
  same as `make gate`'s `FRAMECRAFT_OFFLINE= $(MAKE) up`. After the run, a
  Node one-liner (copied from `make gate` step 5) reads
  `artifacts/e2e/results.json` and fails the job on any `stats.skipped` or
  any test whose `expectedStatus != "passed"` (`test.fail()`'s xfail
  analogue). On failure, uploads `artifacts/e2e/**` and `artifacts/logs/**`
  as `playwright-artifacts`.

`.nvmrc` added at repo root (`22`) since none existed. Root and
`apps/web/.gitignore` already exclude `.next`, `out`, `playwright-report`,
`test-results` - nothing to add there.

## Deviations from the literal brief, and why

- **No `playwright-report/` artifact.** `playwright.config.ts`'s `reporter`
  is `[["list"], ["json", ...]]` - there is no `html` reporter configured, so
  no `playwright-report/` directory is ever produced by this config; the
  gitignore entries for it look like a leftover from before the JSON
  reporter was added. Uploading a directory that never exists would either
  no-op or hard-fail `upload-artifact` depending on `if-no-files-found`.
  Modifying `playwright.config.ts` to add an `html` reporter was in scope by
  the letter of "do not modify application code except an e2e spec", since a
  config is arguably neither, but I left it alone: the brief's instruction
  was specific and I would rather flag the mismatch than guess at intent.
  `artifacts/e2e/` (results.json + the `outputDir` with
  `trace:"retain-on-failure"` and `screenshot:"only-on-failure"` per test)
  plus `artifacts/logs/` is uploaded instead - it is what a failed run
  actually needs to debug and is a strict superset of what an HTML report
  would show for a single run.
- **The Overpass fixture at `tests/fixtures/overpass-chicago-loop.json`
  (12,725,477 bytes) is not wired in anywhere**, and I did not modify any
  e2e spec. Two independent things are true and both matter:
  1. It is byte-identical to the already-committed preset fixture
     `fixtures/a4e5375818f309940313e0ac08b8ebb88c615f9e.json` (rotation 0,
     the exact Chicago-Loop-at-rotation-0 raw response, per
     `fixtures/presets-index.json`). It cannot serve the A2 "low coverage"
     test in `smoke.spec.ts` (wrong location - full Loop data would break
     the `<20 buildings` assertion) and it cannot serve the rotation-nudge
     touch either (a 1 degree rotation is a different bbox, hence a
     different sha1 cache key from the one this file already duplicates).
  2. Playwright `page.route()` cannot intercept any of this anyway: the
     browser never talks to Overpass. It POSTs to the *local* bake API's
     `/scene`, which calls `overpass-api.de` / the kumi.systems mirror
     itself, server-side, over `httpx`
     (`services/bake/app/ingest/overpass.py`, hardcoded endpoints, no env
     override). `smoke.spec.ts`'s own network listener watches
     `${API_URL}/scene` responses, not requests to Overpass, which is the
     tell. Route-mocking a request that is never made from the browser
     would silently do nothing.

  What I found instead, reading the specs closely: of the three places a
  live Overpass call can really happen, two (the rotation nudge in
  `smoke.spec.ts` line ~292 and the advisor-radius click in `ui.spec.ts`
  line ~499) assert only that a `POST /scene` fired, never that it
  succeeded, by design (both have comments to that effect) - so those two
  already "tolerate it via fixtures" in the sense the brief's first option
  describes, and CI needs no change for them. The third, the A2 "low
  coverage" test in `smoke.spec.ts`, genuinely requires a successful,
  content-bearing Overpass response for a real point in Lake Michigan (it
  asserts on the resulting warning text) - this is not incidental, it is the
  test's whole point, and 01/A2 plus the v2-07 audit deliberately turned this
  from a conditional skip into a hard failure specifically so an unreachable
  Overpass could never be mistaken for a pass. `RUNBOOK.md` section 5's
  "exactly one live-Overpass touch" underselling A2 is imprecise for the
  same reason I ended up not touching this: there are three touches, not
  one, but the two the RUNBOOK is probably describing are already inert to
  failure and the one it omits (A2) is required to succeed by design.

  I attempted to neutralise A2 anyway by pre-seeding its exact fixture cache
  entry (`load_raw()` checks `fixtures/<sha1-of-query>.json` before any
  network call, the same mechanism the six presets use, so a correctly-keyed
  fixture needs no app code change at all) - I confirmed this sandbox has
  live Overpass reachability and fetched the real (empty) response for
  `(41.9, -87.45)`. I then deleted it: the sha1 key is over the *exact*
  query text including a 7-decimal-place bbox, and the real value the test
  submits is whatever pixel MapLibre resolves the click to in a headless
  Chromium render (the test itself only asserts that landing is within 6 px
  of the intended target), which I cannot reproduce bit-for-bit without
  actually running the browser - and I was told not to run Playwright
  locally this session. A wrong-keyed fixture sitting in `fixtures/` would
  have been silent, unused clutter, not a fix, so I left the tree as I found
  it. **Net effect: the `e2e` job needs outbound internet access to
  `overpass-api.de`/`overpass.kumi.systems` for one test.** `ubuntu-latest`
  has it by default, and this exactly reproduces what a native `make gate`
  already does and already asserts must succeed (`RUNBOOK.md` G4/G7). This
  is a pre-existing, deliberate project requirement CI inherits, not a new
  CI weakness; the residual risk is ordinary public-API flakiness
  (timeout/rate limit), which would also fail a local `make gate` run.

## Estimated job time (extrapolated from this host's numbers in RUNBOOK.md
   section 4, not measured on GitHub's runners)

- bake-service: pytest alone measured ~4 min on this host for the full 601
  (now moving) test count; budget the 15 min timeout mostly for `uv sync`
  cold-cache time on a fresh Linux runner.
- web: lint + typecheck + vitest are seconds; `next build` is the bulk.
- e2e: native `make gate`'s Playwright phase was ~4 minutes end to end
  including one live Overpass round trip; budget the 30 min timeout for
  Chromium + OS dependency install plus first-run `uv`/`next dev` cold
  starts on a fresh runner.
