Scope: `apps/web/**`, coordinating with the parallel `p3-geometry` builder who
owns `lib/engine/terrain/**`, `lib/engine/solid/**`, `lib/engine/engine.ts`
and `lib/transform.ts`. Everything below is UI/store/panel work built against

## 1. TERRAIN group

New `apps/web/components/editor/groups/TerrainGroup.tsx`, a new panel group
(`lib/groups.ts`, id `"terrain"`, collapsed by default). Controls:
`terrain.enabled` (Toggle), `terrain_exaggeration` (Slider, moved out of
`SurfaceGroup` -- it now belongs beside the toggle that turns terrain on, not
in the roads/water/trees group it was parked in while terrain was flat MVP
scaffolding), `terrain.smoothing` (Slider, 0-5). Inline notes: a "Fetching
elevation data..." note while loading, an error note (`terrain-error`) with
the fetch's own message on failure, an `AuditFinding` id `terrain-low-relief`
surfaced verbatim as a hint the moment the engine reports one, and an
attribution line (`terrain-attribution`) reading `TerrainGrid.source` once a
fetch succeeds (Mapzen's Terrarium credit).

Store wiring (`apps/web/store/editor.ts`): a second debounced job,
`scheduleTerrainJob`/`runTerrainJob` (400 ms, `TERRAIN_DEBOUNCE_MS`),
completely separate from the existing WASM engine job -- it never calls
`generate()`/`engineClient.ingest()` and cannot mark `scene.stale`. Scheduled
from the four location writes (`setPin`/`setRadius`/`setRotation`/
`applyPreset`), from `applyShared`/`resetParams`, and from `setParam` only for
`"terrain"`/`"terrain_exaggeration"`. Cached by `lib/terrainCache.ts`
(`terrainCacheKey`: pin rounded to ~1 m, radius, rotation, exaggeration,
smoothing -- exaggeration is over-inclusive per `fetchTerrainGrid`'s own
docstring but kept per the brief's explicit key shape, see DECISIONS). New
`EditorState.terrain: TerrainState` (`idle|loading|ready|error`, the grid, the
error, the key it was fetched for). `cancelEngineJob()` now clears both
timers. `runEngineJob` passes `terrain: params.terrain?.enabled ?
state.terrain.grid : null` into `engineClient.bake()`.

Protocol/client (`lib/engine/protocol.ts`, `lib/engine/client.ts`, mine, E4's
files, not p3-geometry's): `BakeWireInput` is `EngineInput` again (was
`Omit<EngineInput, "terrain">` with a hardcoded `terrain: null`), since
`EngineInput.terrain` is now a `TerrainGrid` (structured-clone-friendly), not
a `TerrainSampler` (a function value, could never cross the worker boundary).
`runOneBake` passes `msg.input` straight through.

## 3. HEROES (auto-detect)

`lib/heroes.ts` extended with `heroCandidates` (scores every building: `0.5 *
normalised height + 0.2 * normalised footprint area + 0.3 * landmark bonus`,
sorted best-first, deterministic tie-break by id), `autoHeroIds` (manual ids
first, never evicted; fills the auto quota from the best-scoring candidates
not already manual, capped at `HERO_CAP`), `effectiveHeroIds`,
`heroDisplayName`, `topHeroName`, `heroTokenInfo`, `effectiveHeroHeightKey`.

`BuildingsGroup.tsx` gained an "Auto-detect heroes" toggle
(`hero_auto.enabled`) and count slider (`hero_auto.count`), plus a read-only
"Auto-detected" list (`hero-auto-item`) of the auto-only ids (name or
"unnamed building", plus height) -- kept SEPARATE from the manual "Hero
buildings" list on purpose, see DECISIONS for why a shared Remove button would
be a real bug. The manual list itself now shows names too
(`heroDisplayName`), not bare OSM ids.

`{hero}` (`lib/tokens.ts:format_hero`) now prefers `TokenContext.hero_name`
(the top-scoring effective hero's OSM name) over the bare count, falling back
to the count with no name and to `""` with nothing picked.
`lib/previewText.ts:textTokenContext` and
`components/editor/groups/FrameTextGroup.tsx`'s own context builder (the live
"Cuts as:" preview, which does NOT depend on engine timing) both compute it
via `heroTokenInfo`. `services/bake/app/geom/tokens.py` is unchanged (see
DECISIONS for why that is correct, not a gap).

`lib/warnings.ts:predictedTopMm`/`predictedTopDeps` now substitute the
EFFECTIVE hero id set before calling `transform.predicted_top_mm`
(`effectiveParamsForHeight`), so an auto-promoted hero's true-height boost
reaches the 60 mm guard and the HUD exactly like a manual pick already did,
without touching `lib/transform.ts`. `store/editor.ts:currentHeroIds` does the
same for the real bake (`EngineInput.heroIds`), so auto-promoted heroes get
real hero height/colour treatment in the exported file too, not only the
client preview. `CityPreview.tsx`'s hero highlight colour and the keyboard
cursor's "hero" announcement read the same effective set.

One PRE-EXISTING, unrelated failure found while running the full file:
"the detail chip follows the plate, and names a radius that would fix it"
(line 416) times out waiting for the Overpass POST count to move by 1 after
clicking the advisor's "Use 280 m" button. Diagnosed with temporary logging
(added, verified, reverted -- no trace of it left in the diff): `generate()`
does run and does call `EngineClient.ingest()`, which does post an "ingest"
message to the worker, but `fetchOverpass` is never reached for it within the
test's 16.5 s budget. The mechanism is `runBakeJob`'s own documented property
(`protocol.ts`'s module docstring): a bake runs with "no yield points", so it
blocks the worker's single JS thread synchronously until it returns, and an
"ingest" message queued behind a still-running, full Chicago-scale bake (this
test drives `plate_mm` 256 then 100 immediately beforehand, each scheduling a
debounced re-bake of the 992-building scene) simply waits. Reproduced
deterministically twice, on a clean rebuild, with no other heavy process
running on the host -- not a load-related flake. Not caused by this task's
diff: `hero_auto`/`terrain` are both off by default (the test's state), so
`currentHeroIds`/the terrain grid lookup this task added to every bake job
are O(1) early returns, not a new source of the delay. Flagged to the
orchestrator directly at the time; FIXED PROPERLY since, see section 9 below
-- the diagnosis above turned out to be the whole story, not a symptom of
something else, and the team lead asked for the real fix rather than a
workaround.

## 9. The worker-blocking defect: a real product fix, not a workaround

The e2e diagnosis in section 7 was correct and complete: `runBakeJob`'s
"no yield points" property means a worker running a bake is unresponsive to
ANY other message -- including an ingest -- until it returns, and that is
true regardless of `hero_auto`/`terrain`. The team lead asked for the actual
fix: `lib/engine/client.ts`'s `EngineClient` now runs ingest and bake on TWO
ENTIRELY SEPARATE `Worker` instances (`ingestTransport`/`bakeTransport`),
never one shared between them. `worker.ts`/`protocol.ts` needed no change --
both already dispatch by message kind, so a worker dedicated to one kind
simply never receives the other. Constructor changed from a single
`Transport` parameter to `EngineClientTransports { ingest?, bake? }`;
`createEngineClient()`'s zero-arg call is unaffected. Transport-level error
handling is now scoped per worker too: an ingest worker crash no longer
incorrectly rejects a bake in flight on the separate bake worker, and vice
versa (`client.test.ts`'s old single "onerror rejects everything" test split
into two, one per direction).

New `lib/engine/client.supersede.test.ts`: proves, via the in-page fallback
transport and a mocked, artificially slow (delayed, non-blocking) `bake()`,
that `EngineClient.ingest()` never waits on a bake promise -- neither one
still running, nor one just superseded while running. A separate file from
`client.test.ts` because `vi.mock("./engine", ...)` would otherwise disable
that file's own real-bake tests. `client.test.ts` itself updated throughout
to use two mock workers (`ingestWorker`/`bakeWorker`) instead of one shared
one, since ingest and bake messages no longer arrive on the same transport.

Verified against the real e2e this was written for: `e2e/ui.spec.ts`'s "the
detail chip follows the plate, and names a radius that would fix it" now
passes UNMODIFIED in ~9 s (was timing out past 15 s). Full `apps/web`
`npx vitest run`: 1061/1061 across 62 files. `npm run typecheck`/`npm run
lint`/`npm run build` all clean.
